Cluster-native reBot cell

How the reBot printer-tending cell moves from "a script on a laptop drives the cluster" to "the cluster holds the logic", using Intrinsic Core's own pieces: skills, services and the world. Status is measured against main: what is in the branch feat/cluster-native-flow, and what is still open.

Scope: the reBot solution's registration, grasp planning and configuration. The print-to-pick flow (a printer's job becoming a part in the cell) and the work on storing the behavior tree as a process asset are separate, on other branches, and are not covered here. Two small pieces written on the print-to-pick branches, the registration skill and the geometry of A's frames, are used here as they are.

The configure tool resets the simulation as part of its call, so Gazebo matches the belief world afterwards. omts_app does not reset it: after a deploy that leaves Gazebo running, with no configure run, Gazebo keeps the last run's state and the first run can find no part.

Decisions

Each row has what was done, what else was considered, and why. "Decided" means the team chose it when asked; the other rows are choices made while building, open to review.

1. The cell registers its pose estimator itself, on every start

In feat/cluster-native-flow
Done
The skill ai.omts.register_pose_estimator trains and saves the estimator through the train service, and returns at once if it is installed. A new optional vision.registration config section puts it ahead of the perception step. The skill is declared by OrbbecVision, outside the retry, so a failed training is not retried three times.
Instead
The command-line registration tool, run by hand after every deploy. A deploy removes the registration, so the cell was unusable until someone ran it.
Why
Nothing found keeps the estimator across a deploy: a deploy removes installed assets the solution does not declare, and an estimator is created by training at run time, not built. Registering on every start is the answer that needs no manual step.
Result
After a deploy, with nothing registered by hand, the first run registered the estimator and finished in 62 s; the next run logged "already installed" and finished in 57 s. A part that had never been registered (the benchy) was registered during its first run.
Cost
Registering again under an existing id keeps the old settings, so a changed prompt or threshold needs a new estimator id. The config's single threshold also does not follow the per-target value in targets.yaml; all are 0.25 today.

2. A skill computes the part's pose and the grasp frames

In feat/cluster-native-flow
Done
ai.omts.plan_cuboid_grasp takes the pose estimate, composes it with the camera's pose from the world, moves the part's world object, checks the minimum height, and creates or moves the grasp and pre-grasp frames. It also returns the three poses.
Instead
A skill that returns the frames for update_world to write. That needs CEL values inside a world update, which was not tried.
Why
One place does the pose, the height check and the frames, with typed parameters and a unit-testable body. A skill can be called from other trees.
Cost
It edits the belief world directly, so its footprint locks the world (it must not run in a parallel node), and it cannot be previewed (decision 4). A missing camera or parent object is an error.

3. The grasp rule is a plain function

In feat/cluster-native-flow
Done
The rule lives in src/core/grasp_math.py, which imports nothing from intrinsic and has unit tests. cuboid_sweep, which kept its own copy, now calls the function; its output is identical on a sweep of 3 sizes by 4 yaws.
Instead
A copy of the rule in each place, kept equal by a comment ("keep in step").

4. The skills cannot be previewed, and the pick cannot be anyway

In feat/cluster-native-flow
Done
The two skills in the tree refuse preview, because a preview world is taken for the real one and these skills edit the belief world. configure_cell is not in the tree.
Checked
Configpreview and fast_preview
With registrationThe registration skill refuses, 4 s in.
Without registrationThe moves, the capture and estimate_pose_multi_view preview; plan_cuboid_grasp then fails reading estimates[0], because a preview returns zero estimates.
Result
The vision-guided pick cannot be previewed here: the failure is in what perception returns, and the grasp step has nothing to work from. Preview still reaches the moves before perception.
Ask
Is it expected that a preview of estimate_pose_multi_view returns no estimates, and is there a way to give it some?

5. Changing the cell is one skill that applies, and the checks stay on the host

DecidedIn feat/cluster-native-flow
Decision
ai.omts.configure_cell applies a change; it does not judge it. The checks (reach, clearance, inverse-kinematics sweeps) need numpy, scipy and the arm's and printer's meshes, and stay a host tool that runs first.
Instead
Running the checks inside the skill: heavy images and the offline kinematics ported. Or no skill: the host tool applies the update itself.
Done
Every group of values is optional and independent: the printer's distance, the camera mount, the view, A's frames, the part on the bed, parked objects. They apply in one world update, so all or none. Everything is read from the live world, so the skill needs no constants from the checkout. configure_cell --apply runs the checks and then calls it.
Result
One call (about 20 s) replaces three generated files and a manual apply step. The printer and camera values match the file tool exactly, the part and A's frames match to its 4-decimal rounding, the view matches to rounding with its orientation within 0.1 degree. Restoring the defaults through the skill returned every pose to the baseline within 0.03 mm.
Cost
It changes the belief world only; Gazebo follows because the tool then starts an operation from the belief world, which resets it. It cannot be previewed.

6. The view follows the printer and the camera mount

In feat/cluster-native-flow
Done
Moving the printer moves the camera's place at the view by the same distance; changing the mount solves the arm's pose for the view again, so the camera sees the bed as it did. The skill derives this from the live camera, tool and flange poses.
Instead
The host tool's way: start from the committed view each time. Equivalent when the world is at its committed state, and not when it is not.
Checked
A unit test with real transform maths, including the invariant that after a mount change the camera at the new view is where it was at the old one.

7. The part's resting place comes from a parameter, relative to the printer

DecidedIn feat/cluster-native-flow
Decision
The skill takes the bed's top-centre in the printer's frame (bed_top_in_printer_m), and combines it with the printer's pose, which it reads or sets in the same call. A printer move therefore carries the part with it. The host tool reads the value from the printer model's mesh and passes it.
Instead
A named bed frame on the printer model, which the skill would read. It means changing the model.
Done
Each placed object is reparented to the parent first, so a part left in the gripper by a failed run is freed. The parking places are the tool's convention; the skill places objects where it is told.
Result
With the printer at 0.62 m the part's pose matched the file tool's (0.59049, 0.00001, 0.15843 against 0.5905, 0, 0.1584), and a full cycle ran in the moved cell. A part of another shape (the 3D benchy) was placed, registered and picked in a clean deploy with test parts.
Cost
The lying orientation (model z along the world x) is covered by unit tests but was not run live.

8. A's frames are plain geometry that follows the part's height

In feat/cluster-native-flow
Done
A's three frames come from the tilt, A's radius and bearing and the part's half height, in src/core/drop_off.py, whose test keeps it equal to the research tool's numpy version. The skill moves a frame that exists and creates one that does not, in the same update as the rest.
Result
For a part of half height 0.02 m the skill's three frames matched the file tool's (heights 0.02, 0.0407, 0.1407; orientation identical).

Open questions

Four remain for the work above. The full list, which also covers work not described here, is in research/CLUSTER_NATIVE_HANDOFF.md, section 4.

QuestionWhy it matters
Should the tree read its per-run values from the cluster?The part's object, scene-object id, pose estimator and the return area's centre are fixed when the tree is built, which is why app_config.yaml is the one file left. Reading them from the blackboard would remove it, at the cost of a tree change.
Per-target thresholds are not carried into vision.registrationAll 0.25 today; a new target with another value would be registered with the wrong one.
Reconciling with the print-to-pick branchesThey carry their own copies of the registration skill and A's-frame geometry; the files that differ only in comments would conflict.
The rules_oci importIt makes Bazel suggest bazel mod tidy, which would break the build (explained in MODULE.bazel). Needed so a Python skill has a base image.

What we would like reviewed

1
Is a skill that edits the belief world in execute (a footprint that locks the world, no preview) an acceptable pattern for the cell's planning and configuration steps, or should the edits go through update_world?
2
Registering the estimator on every start is the only answer found to a deploy removing it. Is there a way, or a plan, for a deploy to keep an installed asset the solution did not declare, or to declare a trained one?
3
A preview of estimate_pose_multi_view returns no estimates, so the vision-guided pick cannot be previewed. Is that expected?
